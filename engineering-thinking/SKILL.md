# 工程思维

资深工程师的推理框架——先诊断、再动手，而不是急着贴第一个看似合理的补丁。

## 何时使用

**触发条件：** 修 bug、重构、实现功能、审查代码/PR、排查生产问题、理解陌生仓库，或做任何非平凡代码改动。

**不触发：** 单行取值、纯文案/i18n 键、明确无歧义的一处微改、纯解释性问答。

判定模糊时偏向使用。

## 意图分流（加载后第一步）

识别用户意图，只套用对应的约束子集——不要非黑即白：

| 类别                | 信号                                     | 套用                                      | 可省略                     |
| ------------------- | ---------------------------------------- | ----------------------------------------- | -------------------------- |
| **A. 非平凡改动**   | 修 bug、重构、新增模块/接口              | 完整 10 阶段 + 开发规范                   | 无                         |
| **A2. 小改动**      | 调参、改值、加字段等目标明确的低风险改动 | 定位→取证→最小改动→验证（计划可极简）     | 完整假设评分、正式回滚策略 |
| **B. 咨询/分析**    | 为什么、怎么做、帮我分析                 | 用工具验证事实，2-3 句建议 + 取舍，不代决 | 全部写码约束               |
| **C. 配置/部署/CI** | 环境、secrets、CI 流水线                 | 计划优先，外部动作需用户确认              | 代码审查要点               |

**跨类流转：** 任务可从 B（咨询）转为 A（动手）。每进入新阶段重新套用对应约束。

## 核心工作流

```
观察 → 理解 → 定位 → 建立上下文 → 假设 → 取证 → 计划 → 修改 → 验证 → 审查
```

| #    | 阶段   | 做什么                               | 产出       |
| ---- | ------ | ------------------------------------ | ---------- |
| 1    | 观察   | 读取现象，复现问题，不下结论         | 事实记录   |
| 2    | 理解   | 建立系统模型，理解子系统职责         | 心智模型   |
| 3    | 定位   | 找到确切文件 / 函数 / 行             | 具体位置   |
| 4    | 上下文 | 读调用方、被调用方、配置、git 历史   | 上下文充分 |
| 5    | 假设   | 列 2-5 个候选根因，按概率打分排序    | 假设列表   |
| 6    | 取证   | 收集证据证明或证伪每个假设           | 置信度评估 |
| 7    | 计划   | 写修改计划：根因、涉及文件、回滚策略 | 书面计划   |
| 8    | 修改   | 做针对根因的最小改动                 | 代码变更   |
| 9    | 验证   | 编译→测试→日志→边界→回归→审查 diff   | 验证通过   |
| 10   | 审查   | 对照计划自检，确认修的是根因不是症状 | 最终确认   |

完整定义：`references/workflow.md`

### 禁止的流转

| 从   | 到   | 原因             |
| ---- | ---- | ---------------- |
| 观察 | 修改 | 跳过了理解和计划 |
| 假设 | 修改 | 跳过了取证       |
| 修改 | 完成 | 跳过了验证       |

## 执行约束

通过「阶段标记 + gate 脚本 + 置信度」三层机制保障工作流执行。

### 1. 阶段标记（强制输出）

每进入一个阶段，先输出标记再展开工作：

```
【观察】读取错误信息...
【定位】搜索关键字...
【计划】修改计划如下...
【修改】开始编辑...
【验证】运行测试...
```

若发现自己要写代码但尚未输出过「计划」标记——停下来，先补计划。

### 2. Gate 脚本（硬门禁）

`scripts/gate-check.sh` 提供可执行的门禁检查，在关键节点调用：

```bash
# 任务开始时初始化
bash scripts/gate-check.sh init

# 记录阶段流转
bash scripts/gate-check.sh stage 观察
bash scripts/gate-check.sh stage 定位

# 写完计划后记录
bash scripts/gate-check.sh plan set

# 记录置信度
bash scripts/gate-check.sh confidence 75

# 编辑文件前检查（自动拦截：无计划/低置信度/超编辑上限）
bash scripts/gate-check.sh edit src/main/java/Foo.java

# 查看当前状态
bash scripts/gate-check.sh status

# 新任务时重置
bash scripts/gate-check.sh reset
```

门禁拦截规则：

| 检查点     | 拦截条件            | 脚本返回                        |
| ---------- | ------------------- | ------------------------------- |
| 编辑文件前 | 未记录计划          | `GT-002` 错误，exit 1           |
| 编辑文件前 | 置信度 < 40%        | `GT-003` 错误，exit 1           |
| 编辑文件时 | 同一文件编辑 ≥ 2 次 | `GT-004` 错误，自动标记恢复模式 |

### 3. 置信度自评

置信度必须有证据支撑，不是直觉。记录后由 gate 脚本在编辑时自动检查：

| 置信度 | 允许的行动                           |
| ------ | ------------------------------------ |
| < 40%  | 禁止修改，继续调查                   |
| 40-70% | 仅做小的可逆探针（加日志、守卫子句） |
| > 70%  | 按计划推进完整修改                   |

**提升置信度：** 证据确认假设；假设解释所有症状；修复与架构一致。
**降低置信度：** 解释不了次症状；需动大量无关文件；无法复现；修复是压制症状。

## 根因概率评分

按基础概率排序候选根因，优先调查概率最高的：

| 候选原因        | 基础概率 | 典型信号                |
| --------------- | -------- | ----------------------- |
| 配置 / 环境     | 90%      | 本地能跑，线上失败      |
| 数据问题        | 70%      | 仅特定记录触发          |
| 近期改动        | 60%      | 某次提交后出现          |
| 并发 / 竞争     | 40%      | 间歇性、依赖负载        |
| 生命周期 / 时序 | 35%      | 仅启动期或仅长跑期      |
| 事务边界        | 30%      | 写入后读取不一致        |
| 接口契约        | 25%      | 调用方/被调用方版本错位 |
| 线程安全        | 20%      | 共享状态、无同步        |
| 逻辑错误        | 15%      | 总是可复现、确定性      |
| 运行时 bug      | 1%       | 排除一切后才考虑        |

这些是先验概率，根据收集到的证据调整。详见 `references/investigation.md`。

## 防循环护栏

同一区域编辑 ≥ 2 次且问题依旧 → **立即停止编辑**，进入恢复模式：

1. 总结已尝试内容与每次失败揭示的信息
2. 停止修改，回退上次失败改动
3. 重新搜索代码库，用全新视角
4. 重绘调用图，找"假设过但未验证"的环节
5. 形成新假设，置信度 > 40% 后才恢复编辑

**恢复前必须满足：** 新假设不同于失败假设 + 有新证据支持 + 针对不同层/文件/机制。

完整协议：`references/anti-loop.md`

## 开发规范

详见 `references/dev-conventions.md`，核心要点：

- **极简编码**：做被要求的事，不做没被要求的；三行重复优于过早抽象
- **最小改动**：一个问题 → 一个提交 → 一个逻辑改动
- **工具优先**：不确定时用工具验证，不凭记忆
- **编辑前先读**：禁止盲改文件
- **防御性编程**：不信任外部数据归属，关键结果落盘，先查再建
