# 架构思维

修改系统前，先在脑中建立其结构的地图。若你无法把 bug 位置放到架构中，就说明你还没足够理解它，不足以安全修复。

## 规则

> 若不理解架构，就继续读。不要写。

编辑你不懂上下文的代码，正是回归的根源。

## 先建地图

对任何系统，在动代码前先识别各层及其间的数据流。

### 常见架构

**分层 / 单体（如 Spring、Django、Rails）：**

```
Controller  →  Service  →  Repository  →  Database
    ↑              ↑            ↑
  HTTP         业务逻辑      数据访问
  处理          / ORM
```

**微服务：**

```
Gateway  →  Feign/HTTP 客户端  →  Provider 服务  →  DB
    ↑              ↑                    ↑
  路由          服务间调用          业务逻辑
  / 鉴权
```

**事件驱动：**

```
Producer  →  消息队列  →  Consumer  →  DB
                              ↓
                          副作用
                      （邮件、缓存等）
```

**前端 SPA：**

```
Component  →  Store/State  →  API 客户端  →  后端
    ↑                              ↑
  UI 渲染                     HTTP / fetch
```

## 如何建地图

1. **找入口点。** 请求 / 事件 / 用户操作从哪里进入系统？（路由、处理器、main、index）
2. **端到端追踪一条路径。** 跟随单个请求从入口到 DB / 响应。记下它跨越的每一层。
3. **识别边界。** 一层在哪里交给另一层？每个边界的契约是什么？
4. **定位共享状态。** 缓存、数据库、消息队列、全局状态——数据存在哪，谁读谁写？
5. **注意异步边界。** 后台任务、定时器、事件监听器——这些是时序 bug 的常见来源。

## 架构不清晰时

若地图不完整：

- 读 README / 文档 / 架构决策记录。
- 读目录结构——包名常能揭示分层。
- 找配置文件（路由、DI、装配）——它们定义了结构。
- 搜索主入口点并外扩追踪。
- 在仓库里找已有图（docs/、architecture/、*.puml）。

**不要猜架构。** 若无法通过读代码确认某层存在，把它当未知并调查。

## 把 bug 放进地图

地图建好后：

- 症状起源于哪一层？
- 请求经过哪些层才到达它？
- bug 是否其实在上游层（输入错）或下游层（脏数据 / 缺依赖）？

数量惊人的"Service 层 bug"其实是 Configuration 或 Data 层的问题在 Service 层浮现。地图告诉你该去哪找。

## 地图维护

心智地图在长会话中会退化——代码被编辑、假设过时。若你已工作一阵或代码库变了（git pull、同事编辑），在下一次修复前为受影响区域重建地图。
