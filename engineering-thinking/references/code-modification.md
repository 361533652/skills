# 代码修改原则

像资深工程师那样改代码：最小、精准、可追溯。目标是恰好改动根因所需——不多不少。

## 首要指令：最小改动

> 改动能修复根因的最小代码量。

修 bug 不是重构、重命名、重排格式或"顺手改进"无关代码的机会。每多改一行，就多一行可能回归、必须审查、污染 diff 的代码。

### 允许

- 改动实现根因修复的确切行。
- 增加能复现 bug 并验证修复的测试。
- 若修复改变了文档化行为，更新注释或文档串。

### bug 修复中禁止

- 为修一个 bug 重写整个服务或类。
- 重命名未直接相关的变量 / 函数。
- 重排格式（空白、import 顺序、括号风格）。
- "顺便"重构——留到专门的 PR。
- 改错误信息，除非信息本身就是 bug。

## 一个问题、一个提交、一个逻辑改动

每个提交必须恰好解决一个逻辑改动。

```
一个问题
  → 一个提交
  → 一个逻辑改动
```

### 为什么

- 聚焦的 diff 才好审查。动 12 个文件 500 行的 diff 没法审查。
- 若需回退修复，单一目的的提交能干净回退。
- 只有提交在逻辑上原子化，git bisect 才有效。
- 责任归属 / 历史保持有意义。

### 若发现多个问题

用独立提交按序修复，每个都有自己的计划和验证。不要把无关的修复混在一起。

## 修改决策树

编辑前走这棵树：

```
根因在此代码中吗？
├── 否 → 不要在此改。找到根因真正所在。
└── 是 → 改动 ≤ 10 行能修吗？
          ├── 是 → 做最小改动。加测试。完成。
          └── 否 → 修复真的需要更多吗？
                    ├── 是 → 在计划里显式界定改动范围。
                    │        说明为何最小改动不够。
                    └── 否 → 你在过度设计。重新计划。
```

## 改动模式

### 模式：在源头修，不在症状处修

```
差：在下游捕获异常并返回默认值
好：在坏值产生的地方阻止异常
```

### 模式：守卫契约，而非实现

若某函数收到非法输入，修复应落在调用方（为何发了非法输入？）或契约边界（校验 / 类型），而非函数深处加一道防御性空判断。

### 模式：根因是配置时，优先用配置而非代码

若根因是缺一个配置值，修复是补上配置，而不是在代码里硬编码兜底。

### 模式：根因是数据时，优先纠正数据而非代码

若根因是数据库里的脏数据，修正数据（并加约束防复发），而不是加代码绕过脏数据。

## diff 卫生

- diff 应像一篇故事："问题在这，修复在这。"
- 提交前删除调查期间加的所有调试 / 日志。
- 确保没有 `console.log` / `print` / `System.out` 泄漏进提交。
- 仅对改动文件用项目配置跑格式化 / lint。
- 确认 diff 不含非预期改动（空白、换行符）。

## 提交前自检

- [ ] 每行改动是否都直接服务于根因修复？
- [ ] 有无"顺便"改动？删掉。
- [ ] 是否有"无修复则失败、有修复则通过"的测试？
- [ ] diff 是否与计划一致？任何偏差都已说明。
- [ ] 调试语句删除了吗？
- [ ] 提交信息是否聚焦在那一个逻辑改动？
