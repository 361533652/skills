# 规划一次修改

修改代码前必须有修改计划。无计划，不动手。这是大多数智能体会跳过的一步，也正是这一步把资深工程师和 Copilot 区分开来。

## 计划模板

在写任何代码前，产出包含以下全部字段的计划。若某字段填不出，这本身就说明还需进一步调查。

```
## 修改计划

### 1. 当前理解
[1–3 句话：系统做什么、哪里不对，用大白话]

### 2. 可能的根因
[唯一最可能的一个根因，作为事实陈述]

### 3. 替代解释
[仍在桌面上其他合理原因，及为何它们概率更低]

### 4. 置信度
[< 40% | 40–70% | > 70%]
[一句话说明置信度依据]

### 5. 涉及文件
[列出每个要改动的文件及具体函数/区域]
[文件：函数 — 为何需要改]

### 6. 预期影响
- 修复：该现象消失什么
- 风险：可能破坏什么——调用方、测试、其他路径
- 副作用：修复之外有意的行为变更

### 7. 回滚策略
[若改动让情况更糟，如何撤销]
[如 `git revert <commit>`，或特性开关，或配置开关]
```

## 置信度门槛

置信度水平决定允许的行动：

| 置信度 | 允许的行动 |
|---|---|
| < 40% | 不要修改。回到调查。 |
| 40% – 70% | 仅做小的、可逆的探针式改动（日志、守卫子句、特性开关路径）。 |
| > 70% | 推进完整修改。 |

### 什么会提升置信度

- 证据（日志、调试器、复现）确认了假设。
- 假设能解释所有观察到的现象，而不只是主症状。
- 修复与架构和既有模式一致。
- 有审查者或文档佐证预期行为。

### 什么会降低置信度

- 假设能解释主症状但解释不了次症状。
- 修复需要动很多无关文件（像是瞎猜）。
- 你无法复现问题。
- "修复"是压制症状（空判断、try/catch 吞掉）而非纠正根因。

## 计划质量检查

退出计划阶段前，确认：

- [ ] 根因是作为"原因"陈述的，而不是症状的复述。
      差："原因就是它抛了 NPE。"
      好："原因是 LoginFilter 未注册，所以 session 的 user 属性从未被设置。"
- [ ] 至少列了一个替代解释，哪怕概率很低。
- [ ] "涉及文件"中每个文件都给出了改动理由。
- [ ] 回滚策略是具体的，而不是"直接 revert"。
- [ ] 计划不包含无关的重构或清理。

## 计划中的反面模式

- **"我直接加个 try/catch"** — 这是压制，不是计划。异常的原因是什么？
- **"我把这整个类重写"** — 范围过大。最小改动是什么？见 `code-modification.md`。
- **"我 90% 确定是 X" 却无证据** — 没有证据的置信度是空想。先取证。
- **空的"替代解释"** — 如果想不出替代解释，说明调查还不够。
