# 调查技巧

像资深工程师那样调查问题：沿因果链追溯到源头，而不是只修补表层症状。

## 核心反面模式

最常见的错误是"症状驱动的补丁"：

```
看到空指针异常
  → 加一个空判断
  → 完成
```

这"修复"了崩溃，但留下了真正的问题：**它一开始为什么是 null？** null 值只是症状，不是根因。

## 正确的因果链

对任何症状，沿因果链向后追溯：

```
症状（如空指针异常）
  → 谁传的这个值？
  → 为什么是 null？
  → 它何时变成 null？
  → 是配置问题吗？
  → 是生命周期 / 初始化顺序问题吗？
  → 是事务边界问题吗？
  → 是线程 / 竞争问题吗？
  → 是契约问题吗（调用方假设非 null，被调用方返回了 null）？
```

不断问"为什么"，直到找到一个"如果修好它，症状就再也不会发生"的原因。那才是根因。

## 调查清单

对每个 bug，逐一走完这些维度。不要跳到第一个看似合理的就停。

### 1. 数据

- 输入数据合法吗？（空、null、越界、类型错、编码）
- 数据库中的数据是否符合预期？
- 是否有数据迁移或回填可能留下了坏状态？
- bug 是否在不同数据下都能复现，还是仅特定记录？

### 2. 配置 / 环境

- 所有必需的配置项是否都存在且正确？
- 在一个环境能跑、另一个不行？差异在哪？
- 环境变量 / 特性开关 / 密钥是否按预期设置？
- 加载的是正确的配置文件吗？（路径、profile、优先级）

### 3. 近期改动

- `git log -- <path>` — 受影响区域近期改了什么？
- `git log -p --since="2 days ago"` — 整个仓库近期改了什么？
- 是否有与症状出现时间相关的部署 / 发布？
- 检查受影响服务的 CI/CD 历史。

### 4. 并发 / 竞争条件

- bug 是间歇性的还是在压力下出现？
- 是否存在共享可变状态和多个线程 / 进程？
- 有锁吗？锁的范围正确吗？
- 两个请求能否交错导致状态损坏？
- 是否有异步回调 / Promise / 协程可能乱序 resolve？

### 5. 生命周期 / 初始化顺序

- 对象在使用前是否完整初始化？
- 是否有 `@PostConstruct` / `init()` / 构造函数顺序依赖？
- bug 是否只在启动时出现，还是只在运行一段时间后出现？
- 资源（连接、会话、文件句柄）是否在使用前被关闭或过期？

### 6. 事务边界

- 操作在事务内吗？应该在吗？
- 数据在别处读取前，事务是否已提交？
- 是否有嵌套事务或传播问题？
- 回滚是否会留下部分状态？

### 7. 接口契约不匹配

- 调用方的假设是否与真实地被调用方的契约一致？
- 被调用方行为是否变了（版本升级、弃用）？
- 是否存在 schema / 序列化不匹配（字段改名、类型变更）？
- 可空性注解（如 `@NotNull`、`Optional`）是否双方都遵守？

### 8. 逻辑错误

- 是否存在差一错误、比较运算符写错、或条件取反？
- 是否有分支因前面的守卫而永远不可达？
- switch / 模式匹配是否缺了默认分支？

### 9. 线程安全（频率低，但破坏力大）

- 共享集合是否在无同步下被访问？
- 懒初始化字段是否未加保护？
- `ConcurrentModificationException` 是否被掩盖？

### 10. 编译器 / 运行时 bug（最后手段）

- 仅在所有上述情况都被证据排除后才考虑。
- 检查该确切运行时 / 编译器版本的已知问题。
- 隔离复现以排除应用层原因。

## 根因概率评分

按基础概率为候选原因打分，优先调查概率最高的。绝不随机调查。这些是先验概率——随证据到达而调整。

| 候选原因 | 基础概率 | 典型信号 |
|---|---|---|
| 配置 / 环境 | 90% | 本地能跑，生产 / CI 失败 |
| 数据问题 | 70% | 仅特定记录触发 |
| 近期改动（git log） | 60% | 症状在某次提交后出现 |
| 并发 / 竞争 | 40% | 间歇性、依赖负载 |
| 生命周期 / 时序 | 35% | 仅启动期或仅长跑期 |
| 事务边界 | 30% | 写入后读取不一致 |
| 接口契约不匹配 | 25% | 调用方/被调用方版本错位 |
| 线程安全 | 20% | 共享状态、无同步 |
| 逻辑错误 | 15% | 总是可复现、确定性 |
| 编译器 / 运行时 bug | 1% | 排除一切之后才考虑 |

## 实例：空指针异常

**错误做法：**
```
UserService:42 空指针  →  加 `if (user != null)`  →  上线
```

**正确做法：**
```
UserService:42 空指针  →  user 为 null
  → 谁调用 UserService:42？ProfileController.update()
  → `user` 从哪来？session.getAttribute("user")
  → session 属性何时设置？LoginFilter.doFilter()
  → LoginFilter 注册了吗？没有——生产环境缺过滤器链配置
  → 根因：生产 web.xml 未注册 LoginFilter
  → 修复：注册过滤器，而不是加空判断
```

空判断会掩盖真正的 bug（缺失鉴权过滤器）并放行未认证请求。追溯因果链才找到了真正原因。
