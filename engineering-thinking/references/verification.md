# 验证

修复未经验证就不算完成。许多智能体停在"代码改完了"——那只是中点，不是终点。

## 验证链

修改代码后，逐阶段走完。不允许跳过。

```
编译 → 测试 → 日志 → 边界情况 → 回归 → 审查 diff
```

### 1. 编译 / 类型检查 / lint

- 能构建吗？（compile、tsc、mypy、go build 等）
- 是否引入了新的类型错误或警告？
- 用项目配置是否通过了 lint / 格式化？
- 若构建失败，修复无效——不要宣称成功。

### 2. 测试

- 跑受影响模块的现有测试套件。
- 跑依赖改动代码的模块（调用方、消费者）的测试。
- 若某测试现在失败，判断：是修复破坏了它（坏），还是测试本身编码了错误行为（更新测试，给出理由）？
- 增加一个能复现原始 bug、且在修复后通过的测试。这个测试必须在修复前代码上失败、修复后代码上通过。

### 3. 日志

- 检查应用日志，看改动是否引入新的警告或错误。
- 检查是否有之前没有的被吞异常。
- 确认预期的日志行 / 指标现在出现（若修复加了日志）。
- 在日志中找性能回归（更慢的查询、超时）。

### 4. 边界情况

测试修复可能影响的边界：

- null / 空 / 空白输入。
- 最大长度 / 溢出输入。
- 并发访问改动代码路径。
- 原始 bug 报告里的确切复现用例。
- 共享该被改函数的相邻代码路径。

### 5. 回归

- 修复是否改变了原本正常的输入行为？
- 被改函数是否还有其他可能受影响的调用方？
- 若改动是共享的，跑更宽的测试套件（不止模块级）。
- 搜索任何改动过的签名 / API 的用法。

### 6. 审查 diff

像审查同事的 PR 那样读完整 diff：

- 每行改动是否都服务于根因修复？
- 是否有散落的调试语句、TODO、或被注释掉的代码？
- 改动是否最小？
- 提交信息是否准确描述了那一个逻辑改动？
- 审查者能否无需追问就理解这次改动为何修好了 bug？

## 验证结果

| 结果 | 行动 |
|---|---|
| 所有阶段通过 | 修复已验证。进入审查阶段。 |
| 测试失败 | 调查：修复坏还是测试过期。 |
| 日志出现新警告 / 错误 | 推进前先调查。 |
| 边界情况崩 | 修复不完整。回到计划。 |
| 检测到回归 | 修复范围过宽。回到计划。 |
| diff 含无关改动 | 提交前清理 diff。 |

## 禁止的结束态

```
改完代码 → 完成                    禁止
改完代码 → 测试通过 → 完成          禁止（没测边界、没审 diff）
改完代码 → "应该能行" → 完成        禁止
```

唯一有效的结束态是：所有验证阶段通过，且 diff 已自检。
