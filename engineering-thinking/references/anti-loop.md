# 防循环协议

编辑循环是代码智能体最常见的失败模式：修改 → 失败 → 修改 → 失败 → 修改 → 失败，每轮都离根因更远。本文件定义如何检测并跳出这种循环。

## 什么是编辑循环

编辑循环指智能体在同一区域反复修改代码却始终没解决问题。每轮都是一次新的猜测；每次失败置信度下降，但智能体继续猜而不是直接重新调查。

```
修改 → 失败 → 修改 → 失败 → 修改 → 失败 ...
```

这正是把 5 分钟修复拖成 2 小时旋涡的失败模式。

## 检测信号

出现以下任一情况时立即进入恢复模式：

| 信号 | 阈值 |
|---|---|
| 同一文件 / 函数被改且问题依旧 | ≥ 2 次 |
| 修复后同一错误信息仍出现 | ≥ 2 次 |
| 不同错误，但在同一代码区域 | ≥ 3 次 |
| 修复引入了之前代码没有的新错误 | 任何出现 |
| 当前任务编辑总次数无果 | ≥ 3 次 |
| 迭代中置信度持续下降 | 任何出现 |

**第一个信号就足够。** 不要等它们全中。

## 恢复模式

检测到循环时，停止编辑。执行以下序列：

```
1. 总结
   - 原始症状是什么？
   - 尝试过哪些改动？（逐条列出每次编辑及其结果）
   - 每次失败揭示了什么？

2. 停止修改
   - 不再做下一次编辑。
   - 若上次失败改动让情况更糟，先回退它。
   - 不要"再试一件事"。

3. 重新搜索代码库
   - 用全新眼光重读该区域，像第一次见。
   - 搜索可能遗漏的相关符号、调用方、配置。
   - 再查 git 历史和近期改动。

4. 重绘调用图
   - 画出完整路径：入口点 → ... → 失败点。
   - 标出每一跳。哪些是已确认、哪些是假设？
   - 找一处"假设过但从未验证"的跳。

5. 重新定位根因
   - 基于失败揭示的信息，形成新假设。
   - 为其打分（根因概率评分）。优先调查概率最高的。
   - 仅当有了新证据、置信度 > 40% 时才恢复编辑。
```

## 循环为何发生

| 原因 | 表现 |
|---|---|
| 修症状而非根因 | 每次只压制一个症状，另一个又冒出 |
| 上下文不足 | 编辑了调用方未知的代码 |
| 层错了 | bug 在数据层却去修 UI |
| 假设因果 | 没有证据就"肯定就是它" |
| 过度编辑 | 每次改动太大，引入新 bug |
| 心智模型过时 | 迭代中代码变了；模型旧了 |

## 硬性规则

1. **绝不在未进入恢复模式的情况下对同一区域做第 4 次编辑。** 三次出局，必须停手重新调查。

2. **失败的修复是信息，不是挫折。** 每次失败都缩小了搜索空间。记录失败排除了什么。

3. **置信度 < 40% 时绝不编辑。** 改为调查。

4. **若修复后同一错误复现，说明修复没触及根因。** 不要重复同类修复。重新假设。

5. **恢复模式中，读 > 写。** 把这一轮用来理解，而不是敲键盘。

## 恢复清单

完成恢复模式、恢复编辑前：

- [ ] 已陈述一个不同于失败假设的新根因假设。
- [ ] 有新鲜证据支持它（日志、复现、调用图）。
- [ ] 置信度 > 40%。
- [ ] 计划说明了之前修复为何失败。
- [ ] 新修复针对与之前不同的层 / 文件 / 机制。

任何一项未勾选，就留在恢复模式。
