# UI 去 AI 味（ui-deai）

审查前端页面源文件，识别并修复典型的 AI 生成痕迹，让界面回归人类设计师的质感。

一句话本质：AI 味重的前端通常不是"丑"，而是**太像一个合格的默认模板**——没有品牌个性、没有基于业务的信息取舍、没有真实产品会有的脏乱和例外。修复不是简单地换色去 emoji，而是要打破"模板感"本身。

---

## 两种工作模式

| 模式         | 触发场景                            | 行为                                       |
| ------------ | ----------------------------------- | ------------------------------------------ |
| **审查修复** | 用户指定已有文件/目录，要求去 AI 味 | 扫描 → 列出问题 → 确认后直接改文件         |
| **实时约束** | 用户正在写新页面，要求避免 AI 味    | 在生成代码时主动遵守规则，不写出 AI 味代码 |

## AI 味检查清单（9 大类）

完整清单含症状描述和修复方向，详见 `references/checklist.md`。以下是速查索引：

| #    | 类别           | 一句话判断标准                                               |
| ---- | -------------- | ------------------------------------------------------------ |
| 1    | 布局套路化     | Hero+三列卡片+统计条+CTA 标准模板；什么都做成卡片；居中对称无节奏 |
| 2    | 排版机械化     | 字号标准步进；通用营销标题；只用系统默认字体                 |
| 3    | 配色 AI 感     | 紫蓝/青蓝渐变；渐变文字标题；黑底+霓虹                       |
| 4    | 视觉效果堆砌   | 全站大圆角；毛玻璃/发光/光斑；组件一个样                     |
| 5    | 装饰元素通用化 | 装饰性 emoji ≥3 个；通用图标；Badge 标签到处贴               |
| 6    | 交互动效套路化 | hover 统一位移+阴影；不必要的 skeleton/modal                 |
| 7    | 内部内容泄露   | HTML 注释可见；调试信息；placeholder 未替换                  |
| 8    | 文案 AI 腔     | "赋能""一站式""Seamless""Powerful"；按钮文字过正式           |
| 9    | 缺乏真实产品感 | John Doe/99.9%/$29mo 假数据；只覆盖理想路径                  |

## 快速识别信号（客观检测，禁止仅凭阅读判断）

**这一步必须运行脚本，不能只靠"读一遍代码觉得没问题"。**

```bash
python3 scripts/scan.py <文件或目录路径>
```

脚本对 8 大类做正则匹配，输出命中的文件、行号、具体文本。退出码 `0` = 零命中，`1` = 仍有命中。

**排版机械化**属于语义判断，脚本无法检测，需人工核查：标题是否只用通用营销模板、字号是否标准步进、是否只用系统默认字体（`PingFang SC`/`-apple-system`/`Segoe UI`/`Microsoft YaHei` 不算"引入个性字体"，必须是 Google Fonts / `@font-face` 等额外加载的字体才算）。

**`total_hits` 必须为 0 + 排版机械化人工核查通过 = "未命中"**，不允许在脚本报出命中时自行判断"不算问题"而跳过。

## 工作流程（审查修复模式）

### Step 1：确定扫描范围

- 用户指定文件：直接扫描
- 用户指定目录：扫描其中的 `.html`、`.htm`、`.vue`、`.tsx`、`.jsx`、`.svelte`、`.css`、`.scss`、`.less` 文件
- 用户没指定：问清楚再动手

### Step 2：逐文件扫描

对每个文件，先运行 `python3 scripts/scan.py <路径>` 拿到客观命中结果，再补充人工核查"排版机械化"。**禁止跳过脚本直接凭阅读判断**。记录：
- 文件路径 + 行号（直接取自脚本输出）
- 问题类别（对照 `references/checklist.md` 的 9 大类）
- 具体问题描述
- 修复建议

### Step 3：汇总报告并确认

向用户展示扫描结果，格式：

```
## 扫描结果：发现 N 处 AI 味问题

### 🔴 严重（内容泄露）
- `src/pages/Home.vue:42` — HTML 注释 "TODO: 替换为真实数据" 会渲染给用户

### 🟡 明显（布局/排版/配色/视觉效果/装饰元素/交互动效/真实产品感）
- `src/pages/Home.vue:15-30` — 典型 Hero+三列卡片+统计条模板，渐变紫蓝背景
- `src/components/Feature.vue:8` — 每个特性标题前都有 emoji，配图是通用抽象插画

### 🔵 轻微（文案）
- `src/pages/Home.vue:55` — "为您提供一站式解决方案" → 建议改为具体描述
```

**问用户：** 全部修复 / 只修严重+明显 / 选择性修复？

### Step 4：修改文件

拿到确认后，逐个修改。每个修改说明改了什么、为什么改。修复时参照 `references/checklist.md` 对应类别的"修复方向"。

### Step 5：改完复查（硬性门槛，不能跳过或走过场）

重新运行 `python3 scripts/scan.py <路径>`，**必须把脚本的真实输出（`total_hits` 数值）贴出来作为证据**，禁止只用"看起来没问题了"收尾，也禁止不跑脚本直接自己写一份"全部未命中"的表格：

```
## 复查结果

scripts/scan.py 输出：total_hits = 0

| 类别 | 命中情况 | 证据 |
|------|---------|------|
| 布局套路化 | 未命中（脚本） | - |
| 排版机械化 | 未命中（人工核查） | 字号已打破标准步进，标题已具体化 |
| 配色 AI 感 | 未命中（脚本） | - |
| 视觉效果堆砌 | 未命中（脚本） | - |
| 装饰元素通用化 | 未命中（脚本） | - |
| 交互动效套路化 | 未命中（脚本） | - |
| 内部内容泄露 | 未命中（脚本） | - |
| 文案 AI 腔 | 未命中（脚本） | - |
| 缺乏真实产品感 | 未命中（脚本） | - |
```

**`total_hits` 不为 0 或排版机械化人工核查发现问题 → 禁止结束任务**，必须回到 Step 4 继续修改，直到全部通过。

### Step 6：优化建议（复查通过后，可选、不阻塞交付）

Step 5 通过只代表"没踩清单红线"，不代表"设计完美"。从以下维度挑 1-3 条真正适用的建议，没有就直接说没有，不硬凑：

- **版式节奏/留白比例**：核心区域是否足够突出
- **组件差异化**：视觉权重是否可以拉得更开
- **微交互细节**：loading、空状态是否贴合产品调性
- **内容真实感**：文案/示例数据是否还能更具体

## 实时约束模式

当用户要求写新页面且要求避免 AI 味时，**必须先完成设计规划再写代码**。

### Step A：生成前设计规划（不能省略）

```
## 设计规划

**产品定位**：工具型/社区型/内容型/娱乐型等；偏严肃还是轻松；如果这个产品是一个人，他是什么性格？参考什么材质的质感？——答不出具体的说明还没想清楚
**用户场景**：用户在什么状态下打开这个页面（匆忙/慢慢看，高频/低频，工作/生活）
**页面主任务**：用户进来要做的最主要的事，哪些该弱化或不做
**视觉策略**：布局/配色/组件风格，为什么不是常见的居中模板、蓝紫渐变、玻璃拟态
**主动规避的坑**：列出这个产品最容易默认套用的 2-3 个 AI 味特征
```

### Step B：写代码时遵守的红线

对照 `references/checklist.md` 的 9 大类，在写代码时**主动规避每一类的典型症状**。核心红线：

1. 不写 Hero+三列卡片+FAQ+CTA 默认模板；不是所有内容都做成卡片
2. 不用标准字号步进和通用营销标题；引入至少一个匹配产品气质的字体
3. 不用紫蓝/青蓝渐变、渐变文字标题、黑底+霓虹配色
4. 不堆毛玻璃/发光/光斑；圆角和阴影不要全站一个值
5. 不加装饰性 emoji；不到处挂 Badge/Tag
6. 不套千篇一律的 hover 动效；不加不必要的 skeleton/modal
7. 不写 AI 腔文案；按钮不用模板文字
8. 不留面向开发者的可见内容
9. 不加编造数字的统计条；不用一眼假的占位数据
10. 布局有节奏变化；配色克制（主色 ≤ 2）；信息密度按内容量走

### Step C：生成完代码后必须自查

对目标文件运行 `python3 scripts/scan.py <文件路径>`。若 `total_hits` 不为 0，直接修改后重新跑，直到为 0，并人工核查排版机械化。不用把自查过程讲给用户看，只交付改好的最终代码。

### Step D：交付时附带优化建议（可选，不阻塞交付）

同审查修复模式 Step 6。

## 约束与注意事项

- **严格按步骤执行（最高优先级）**：禁止自主跳步、合并步骤或调整顺序。只有步骤内明确写了"跳过"条件时才允许跳过
- **必须做的**：
  - 修改前必须先读取文件完整内容，不能凭记忆改
  - Step 3 扫描结果必须展示给用户确认后才能改文件
  - 只改样式、布局和文案，不动业务逻辑和数据绑定
  - Step 2/Step 5 都必须运行 `scripts/scan.py`，贴脚本输出作为证据
  - `total_hits` 不为 0 时禁止收工
  - Step 6/Step D 的优化建议是软性建议，不阻塞交付
- **禁止做的**：
  - 不要在未经用户确认的情况下直接修改文件
  - 不要删除功能性代码（事件绑定、状态管理、API 调用等）
  - 不要凭记忆判断文件内容
  - 不要编造不存在的文件路径或组件名

## 错误处理

| 场景                 | 处理                                               |
| -------------------- | -------------------------------------------------- |
| 用户指定的文件不存在 | 报错，列出当前目录下的前端文件供选择               |
| 文件不是前端文件     | 跳过，告知用户该文件不在扫描范围内                 |
| 扫描后没发现问题     | 告知用户"没有发现明显的 AI 味问题"，给出整体评价   |
| 修改后页面功能异常   | 只改样式和文案，不动业务逻辑；改之前确认不影响功能 |
| 用户对某条修复有异议 | 跳过该项，记录用户偏好                             |
